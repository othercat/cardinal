# #6 按文件实际占用的磁盘空间排序

[GitHub Issue #6](https://github.com/othercat/cardinal/issues/6)

「大小」列显示文件系统报告的磁盘分配量，并用同一数值升降序排列。稀疏文件以 Docker 的磁盘映像为回归样本。本机和移动卷共用此规则，已有索引需保留名字、路径、时间、事件游标，并能在取得分配量后保存。既有 `size:` 搜索语法和小文件事件策略沿用逻辑长度。[总管 #1](issue-01-overall-management.md)

开发时沿用 r7 工作区，当时 `master` 的 HEAD 为 `25a53416cdffa57c5b6205f78af33482df5b58b1`。验收覆盖逻辑长度与分配量顺序相反的文件、真实零占用、旧快照、离线卷、重启与用户提供的 `Docker.raw`。

## r8 实现与升级

Darwin 批量目录和 HFS+ 目录查询同时提取逻辑长度与全部 fork 的分配量。缺少批量属性时读取链接自身的 `st_blocks × 512`。本机与移动卷的列表、即时排序预览、全局排序、分页和文件变更均使用同一分配字节数。不可获取的占用显示「—」，真实零占用显示「0 B」。已有 `size:` 查询和小文件事件节流保持原来的逻辑长度含义。

格式 5、6 按原节点 ID 读入，保存为格式 7。旧文件的日期、逻辑长度、树和事件游标保留。查看单条结果或小范围排序时优先读取所需属性。大范围按占用排序时按目录分批读取，失败时保留旧文件的其他已知属性。首次覆盖旧快照前，在原目录保留同名 `.v5.bak` 或 `.v6.bak` 以供回退。旧卷离线时仍能搜索，重连后核对卷身份、补齐分配量并保存。

## 实机验收

Apple M1 Pro，macOS 15.7.7。仅读取用户指定的 Docker 磁盘映像属性。逻辑长度为 1,099,511,627,776 B，Darwin 批量读取和 `lstat` 返回的分配量均为 8,545,845,248 B，界面格式化为 8.55 GB。

在 #2 的旧索引 APFS 副本上运行生产构建使用的 Rust 库。用 6 个工作线程按当前文件系统补属性，保留快照原有条目和游标，未回放之后发生的事件。计时不包含窗口绘制，未清空操作系统缓存。

| 实测步骤 | 结果 |
| --- | --- |
| 载入格式 6，保留 8,649,106 项 | 9.809 秒 |
| 对包含 Docker.raw 的两个结果首次补属性并按占用排序 | 1.762 毫秒 |
| 按目录处理其余 7,277,204 个待补项 | 96.640 秒 |
| 保存格式 7 | 2.357 秒，226,383,768 字节 |
| 重开加载，再按全局磁盘占用排序 | 载入 9.409 秒，排序 0.756 秒，待补数为 0 |

旧快照中有 202,832 项在本次核对后仍无可用占用值，保留未知状态。本次全局降序中 Docker.raw 排第 3。核对了排序相邻项、原有节点身份、事件游标和条目总数，升级自动留存的 v6 备份与原始只读样本的 SHA-256 相同。

独立 WKWebView 窗口在首次打开和正常退出重启后，通过 macOS 辅助功能实际点击「磁盘占用」列头。两个方向均按 APFS 的分配值排序。1 TiB 全空洞文件显示 0 B、32 GiB 的部分分配文件显示 4.1 KB、稠密文件显示 98.3 KB。HFS+ 和 APFS 映像另行验证了资源叉、稀疏文件、同名卷隔离、旧缓存从离线到重连升级、再次弹出后的排序。真实 FSEvents 覆盖了在稀疏文件内部写入、逻辑长度保持原值且排序位置随占用改变的情况。

根 Rust workspace 1,827 项通过，默认忽略 8 项。Tauri 默认 51 项、额外的移动卷映像测试及按需 HFS+ catalog 测试通过。前端 typecheck、314 项 Vitest、生产构建和两个 Rust workspace 的 Clippy 均通过。
